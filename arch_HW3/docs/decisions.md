# Архитектурные решения

## Границы сервисов

Booking — FastAPI REST, данные пассажира, стоимость и статус бронирования. Flight — gRPC, рейсы и доступность мест. Раздельные PostgreSQL, отдельные роли и миграции. Межсервисные UUID не являются FK. Только тестовый инструмент/проверяющий подключается к обеим БД для SELECT; код приложений этого не делает.

Python выбран для небольшого объёма сервисного кода. Контракт Flight написан в protobuf, сообщения и stub/servicer генерируются настоящим protoc через grpcio-tools. REST-контракт выражен типизированными моделями FastAPI и доступен в `/openapi.json` и `/docs`.

## Согласованность двух БД

Одна локальная SQL-транзакция не может атомарно объединить две независимые PostgreSQL и gRPC. Поэтому здесь локальные транзакции и долговечная компенсация, без заявления о глобальном ACID.

1. Booking сохраняет intent CREATING и fingerprint запроса до сетевых эффектов.
2. Вызывает GetFlight, затем ReserveSeats с booking_id и expected_price.
3. Flight делает SELECT FOR UPDATE и в одной транзакции уменьшает available_seats и вставляет резервацию.
4. Booking одной локальной транзакцией сохраняет CONFIRMED и завершает intent.
5. Если создание не завершается, вызывается ReleaseReservation. При недоступности Flight остаётся COMPENSATING; worker повторяет компенсацию после восстановления.
6. При падении процесса CREATING/COMPENSATING/CANCELLING переживают перезапуск в PostgreSQL. Worker поднимает их; активный обработчик защищён advisory lock, поэтому worker не отменяет ещё выполняющийся запрос.

Снаружи не появляется CONFIRMED-бронирование при неуспешном резервировании. В условиях полного сетевого разделения удалённый резерв может временно оставаться до восстановления связи: это честная граница saga. Постоянного потерянного резерва после восстановления не остаётся благодаря intent и cancellation fence. Неограниченный outage нельзя исправить одной локальной транзакцией.

При отмене intent CANCELLING сохраняется до вызова ReleaseReservation, затем статус меняется на CANCELLED. Если ответ потерялся, worker повторяет безопасный Release и завершает локальное изменение.

## Идемпотентность и потеря ответа

Flight использует UNIQUE(booking_id). Повтор того же flight_id и seat_count возвращает ту же ACTIVE-резервацию. Другие параметры дают ALREADY_EXISTS; освобождённый booking_id повторно не используется. ReleaseReservation идемпотентен и сохраняет tombstone даже для отсутствующего резерва. Это закрывает сценарий «RPC завершился по deadline, отмена пришла раньше запоздавшего резервирования».

На REST есть необязательный `Idempotency-Key: UUID`. Он становится booking_id. Повтор запроса возвращает тот же текущий booking; другие данные с тем же ключом — 409. После неудачной/незавершённой операции повтор не создаёт новый резерв: клиент получает 409 и использует другой ключ для нового намерения. Без заголовка каждый POST — новое бронирование.

expected_price предотвращает подтверждение по устаревшей цене между GetFlight и ReserveSeats. При конфликте 409, клиент запрашивает рейс заново. Сумма берётся из GetFlight и сохраняется снимком; деньги в protobuf/JSON передаются decimal-строками, в Python — Decimal, в PostgreSQL — NUMERIC.

## Кеш и его актуальность

Cache-aside: GET Redis → проверка валидности записи → при miss чтение полного рейса/поиска из PostgreSQL → SET с TTL 300..600 секунд. Логи: cache_hit, cache_miss, cache_invalidated, cache_unavailable.

Ключи: `flight:{uuid}`, `search:{origin}:{destination}:{YYYY-MM-DD|any}`. При CreateFlight/UpdateFlight/ReserveSeats/ReleaseReservation инвалидируются затронутый рейс и поиск по старому/новому маршруту и дню, а также поиск без даты.

Redis реплицируется асинхронно: при failover удаление ключа может потеряться. Есть также гонка заполнения кеша параллельно записи. Поэтому у каждой кеш-записи есть epoch, а PostgreSQL хранит актуальную версию. На cache hit выполняется маленький SELECT версии; полезная нагрузка берётся из Redis только при совпадении. PostgreSQL FOR SHARE удерживает версию на время чтения/заполнения; мутации сначала блокируют версию FOR UPDATE, затем рейс, меняют версию и удаляют ключи в той же критической секции. Версия после rollback не меняется; преждевременное удаление даёт только лишний cache miss.

Цена этой гарантии — один небольшой запрос к БД даже при cache hit и сериализация мутаций через общую строку epoch. Это учебное решение в пользу простоты и строгой актуальности. Кеш сокращает загрузку полных строк/соединений и построение результатов поиска, но не устраняет все обращения к PostgreSQL. Для большой нагрузки понадобилась бы более детальная версия по агрегату/маршруту и отдельный протокол согласования.

При недоступном Redis приложение читает PostgreSQL. Если недоступна сама Flight DB, устаревший кеш как достоверный ответ не выдаётся.

## Redis Sentinel

Один master, две replicas, три Sentinel, quorum=2. Redis-py использует Sentinel.master_for, а не жёстко заданный адрес master. Все узлы находятся в одной Compose-сети, рекламируют доступные DNS-имена. Sentinel автоматически повышает реплику; перезапуск исходного master не требует менять адрес в приложении. В volumes сохраняется переписанная конфигурация.

Это отказоустойчивость при потере отдельных процессов/узлов внутри стенда, не защита от отказа всего Mac: контейнеры находятся на одном физическом хосте. PostgreSQL в задании не кластеризуется.

## Retry и Circuit Breaker

Порядок gRPC client interceptors: Circuit → Retry → API key → сеть. Breaker считает результат одного логического вызова после всех попыток. Retry: максимум 3 попытки суммарно, паузы 100 и 200 ms по умолчанию, только UNAVAILABLE и DEADLINE_EXCEEDED. Бизнес-ошибки не повторяются. Встроенные gRPC retries отключены, чтобы не возникло скрытого умножения попыток. Deadline задаётся на каждую попытку.

CLOSED учитывает последовательные transient-сбои в окне времени; успешный или корректный бизнес-ответ сбрасывает счётчик. При достижении порога OPEN немедленно возвращает HTTP 503 CIRCUIT_OPEN. После reset timeout один запрос допускается в HALF_OPEN. Успех закрывает breaker, transient-ошибка снова открывает. Другие одновременные пробные запросы отклоняются. Результат старого in-flight вызова не может закрыть уже открывшуюся новую генерацию breaker.

Порог, окно, reset timeout, число попыток, backoff и RPC timeout задаются env. Переходы видны в JSON-логах и `/diagnostics`. Worker использует этот же клиент и те же ограничения.

## Аутентификация и область задания

Все Flight RPC, включая операторские методы и Health, требуют x-api-key. Сравнение constant-time; отсутствие/неверный ключ даёт UNAUTHENTICATED. Ключ приходит из env и не логируется. Локальный Compose содержит демонстрационное значение; `.env` исключён из Git. Flight gRPC доступен с Mac только на loopback, PostgreSQL и Redis портов на хост не публикуют.

Это межсервисная аутентификация. JWT пользователей и проверка владельца по access token в этом задании не требуются: user_id передаёт клиент. При публикации системы во внешнюю сеть нужны отдельная клиентская авторизация и защищённый транспорт; данный стенд локальный.

## Альтернативы

| Решение | Преимущество | Цена / причина выбора |
|---|---|---|
| Один сервис и одна БД | Простая локальная транзакция | Не выполняет требование двух микросервисов |
| Выбранные два сервиса + durable compensation | Раздельное владение, обычные локальные транзакции, восстановление после сбоя | Временное промежуточное состояние при outage, нужны worker и идемпотентность |
| Распределённый 2PC-координатор | Другие гарантии атомарности | gRPC сам не является участником 2PC, значительно сложнее и не требуется |
| Redis Cluster | Шардирование | Для маленького кеша не нужно, а 3 master без реплик не дают такую же защиту от потери master |
| Выбранный Sentinel | Автоматическое переключение с репликой и простым клиентом | Нет шардирования, асинхронная репликация требует проверки свежести |
